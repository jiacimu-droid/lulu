# Lulu master 全仓审计报告（2026-07-30）

## 审计范围与方法

本次审计基于 `master@9d0858cc152895f75978b5e6454f7fafcdcdbe56` 的代码索引，对 1,188 个已索引文件、262,736 行代码/文本、5,681 个符号进行全仓结构扫描，并对陪伴聊天、记忆、主动消息、关系承诺、电话语音、学习监督、插件、构建发布及近期改动文件进行重点回读。

需要区分两种覆盖：

- 所有文件均经过索引级检查：路径、模块、行数、符号、依赖、分类、TODO 标记与热点。
- 高风险核心文件进行了内容级检查；没有逐行人工复述全部 26 万行。索引无法证明运行时行为正确，最终仍需编译、测试和真机交互验收。

## 总体结论

仓库功能覆盖已经很丰富，但当前主要风险不是“功能太少”，而是：

1. 新旧实现并存，界面隐藏不等于业务退役。
2. 陪伴核心服务体积过大，修改一处容易影响聊天、记忆、主动消息和电话。
3. 多处采用同名函数、兼容壳或旁路文件改变旧行为，短期快，长期难定位。
4. 产品说明文档与实际实现状态存在过时基线、已完成任务仍标记“进行中”等维护债务。
5. 自动化测试数量不少，但近期 UI 改动没有对应编译证据，不能确认当前 master 可构建。

## P0：应优先处理的问题

### 1. 学习模块存在新旧两套 UI

相关文件：

- `StudyMainPanels.kt`
- `StudyCollectionPanel.kt`
- `StudyCompactPanels.kt`
- `StudyPage.kt`
- `StudyRewardPanels.kt`

`StudyPage.kt` 已切换到新的 Compact 组件，但旧的 Hero、收藏、等级弹窗和大量说明 UI 仍保留在原文件中。结果是：

- 后续开发者很容易修改到没有实际展示的旧组件。
- 新旧界面可能继续读取同一状态，却呈现不同规则。
- 代码索引会把两套实现都当作有效功能入口，增加检索噪声。

建议：确认新 Compact 页面稳定后，删除或明确标记旧组件；共用的小组件抽到独立文件，不保留整套旧页面。

### 2. “取消等级”和“取消通用普通碎片”目前只完成了 UI 隐藏

等级相关状态、规则、奖励、VM 方法和旧弹窗仍存在；通用普通碎片仍存在于模型、规则、商店、说明、迁移和测试中。

风险：

- 后台仍可能产生等级奖励或通用碎片，只是用户看不到入口。
- 旧存档字段持续增长，未来恢复某个旧入口时会重新暴露。
- 产品规则和实际数据模型不一致。

建议：先决定“兼容读取但不再产生”还是“彻底迁移删除”。推荐分两阶段：停止所有新产出和消费；完成存档迁移后再删除字段。

### 3. `StudyRecentEventDisplayPolicy.kt` 用同名 `take` 改写显示数量

该文件通过定义 `List<StudyEvent>.take(count)`，把旧调用 `take(6)` 静默改成 10。这个实现很隐蔽：

- 阅读 `StudyMainPanels.kt` 时仍看到 `take(6)`，行为却是 10。
- 同包其他代码调用 `take(6)` 也可能被意外影响。
- 重构 import 或移动包后行为会改变。

建议：直接把真实调用点改成明确常量 `RECENT_EVENT_DISPLAY_LIMIT = 10`，删除旁路扩展。

### 4. `StudySnackbarHost.kt` 通过同名组件立即 dismiss Snackbar

此实现没有停止消息产生，只是把已排队 Snackbar 立刻关闭。问题包括：

- VM 仍持续发送成功提示，事件流仍有无意义工作。
- 与 Material3 的 `SnackbarHost` 同名，阅读和解析都容易混淆。
- 真正错误提示也可能被一并吞掉。

建议：从 `StudyVM` 区分成功事件与错误事件；成功结果只写奖励记录，失败信息才显示非阻塞提示。删除同名 SnackbarHost 覆盖。

### 5. 当前 master 缺少近期 UI 改动的编译证据

最近提交没有可读取的工作流运行，且审计环境未执行 `:app:compileReleaseKotlin`。因此不能确认新增 Compact 组件、同名 SnackbarHost 与同名 `take` 扩展在当前 Kotlin/Compose 配置下无冲突。

建议：下一次代码修改前先运行一次聚焦 Release Kotlin 编译，修复当前 master 的真实编译基线。

## P1：陪伴感与活人感风险

### 6. `ChatService.kt` 是 3,143 行、126 个本地依赖的超级服务

它同时承担消息、上下文、工具、记忆、电话同步、落库和多种边界处理。陪伴体验依赖这里，但文件过大导致：

- 普通聊天、电话、主动消息很难保证真正一致。
- 小改动容易产生跨出口回归。
- 失败路径和角色输出路径不容易审查。

建议按“回合编排、上下文、工具执行、持久化、角色输出”拆成明确协作者，ChatService 只保留编排。

### 7. `ProactiveMessageService.kt` 达 2,295 行并依赖 90 个本地文件

主动陪伴的生成、时机、状态、通知、反馈、未回复生命周期混在一个服务中。活人感最怕重复、机械和上下文错位，而超大服务使这些行为难以独立验证。

建议拆分：候选事件收集、联系决策、内容生成、发送渠道、反馈学习、生命周期持久化。

### 8. `MemoryBankService.kt` 达 1,874 行、94 个符号

虽然记忆重建计划覆盖较完整，但服务仍过大。批次、召回、存档、失效、重试和诊断混合后，未来再修“记得但不会用”“重复回忆”等体验问题成本很高。

建议按批次状态机、记忆写入、召回、归档/失效、诊断拆分。

### 9. 统一陪伴重建计划状态过时

`COMPANION_REBUILD_PLAN.md` 顶部仍写“进行中”，基线仍为旧提交，但 P0-P6 几乎全部勾选完成。它已经不能准确告诉开发者哪些能力仍未验收。

建议将其归档为实施记录，另建“当前陪伴体验缺口”文档，只保留仍真实存在的问题和真机验收项。

### 10. 活人感规则主要依赖开发规范，缺少自动守门

`AGENTS.md` 明确禁止固定温柔、恋爱、主人、宝贝等角色兜底，这个方向正确，但规范本身不会阻止代码重新加入固定角色话术。

建议增加轻量静态测试：扫描角色出口中的高风险固定话术，并对冷淡、严厉、普通朋友、亲密、敌对/非人角色做契约测试。

### 11. 数字生活入口较多，但存在插件和原生状态割裂风险

日记、收藏、番茄钟、音乐、朋友圈、小游戏横跨原生数据层和 WebView 插件。若角色只能看到部分原生状态，用户实际在插件中的行为无法成为共同经历，会降低连续陪伴感。

建议建立统一 `CompanionActivityEvent` 总线：所有插件活动写入同一种可查询事件，角色上下文只读取该统一来源。

## P1：交互与美观问题

### 12. 设置页和核心 UI 文件过大

典型文件：

- `ChatInput.kt` 1,064 行
- `ChatMessage.kt` 1,117 行
- `ChatMessageTools.kt` 1,166 行
- `TTSProviderConfigure.kt` 1,031 行
- `AssistantBasicPage.kt` 942 行
- `CihaiPage.kt` 974 行

这些文件混合布局、状态、对话框、业务和持久化，导致视觉调整经常连带行为回归。

建议按“页面骨架、内容区、弹窗、状态映射、业务事件”拆分；统一间距、圆角和卡片规范。

### 13. Compact 陪伴卡三列指标在窄屏上存在拥挤风险

“夸夸值 / 今日学习 / 本周学习”三列同时显示，学习值又包含分钟和番茄数，较大字体或较长数值时可能换行、压缩或视觉失衡。

建议真机测试 360dp 宽度和系统字体 1.3x；必要时改为夸夸值单独一行、学习数据双列。

### 14. 角色选择弹窗直接遍历全部角色，不可滚动

旧实现使用固定高度 LazyColumn，新 Compact 实现改成普通 Column。角色较多时弹窗可能超出屏幕。

建议恢复 LazyColumn，并保留当前角色高亮。

### 15. 收藏页一次展开全部画卷，页面会非常长

Compact 收藏页把所有画卷完整纵向展示；画卷数量增长后查找成本高，也会掩盖常用券。

建议券与画卷分区，画卷使用两列卡片、折叠或搜索；已解锁优先。

### 16. 空库存仍允许跳转的按钮语义不一致

剧场碎片和视频解锁卡数量为 0 时仍可点击进入对应馆，这是合理导航，但按钮文案和“使用券”混在同一种 RewardRow，用户不容易判断是消费还是浏览。

建议将动作分为“使用”和“前往”，视觉和文案区分。

## P2：架构与维护债务

### 17. 30 个生产文件超过 800 行，3 个超过 1,500 行

这不是单纯代码风格问题，而是修改风险集中。优先拆分前三名：ChatService、ProactiveMessageService、MemoryBankService。

### 18. 高扇入基础模型修改风险大

`Message.kt` 被约 129 个本地文件依赖，`PreferencesStore.kt` 被约 112 个文件依赖。直接在这些文件增加产品特例会放大回归范围。

建议基础模型保持中立；产品特例放适配层，并对序列化兼容增加测试。

### 19. PreferencesStore 过度集中

953 行且高扇入，说明大量无关设置共享一个中心模型。继续增加电话、学习、主动消息和陪伴设置会让迁移与默认值越来越脆弱。

建议按领域拆设置子模型，同时保持统一序列化外壳。

### 20. RouteActivity 仍承担过多路由与初始化责任

1,032 行、77 个符号、89 个本地依赖。新页面持续加入后，启动、深链、权限和路由容易互相影响。

建议拆为路由图、启动协调器、深链处理和权限入口。

### 21. TODO/FIXME 标记共 32 个

生产代码中值得优先回读的包括：

- `TTSProviderConfigure.kt`（3 个）
- `PluginUIDeclarativePage.kt`（2 个）
- `CompanionPerception.kt`
- `Provider.kt`
- `ServiceAccountTokenProvider.kt`
- `FilesManager.kt` 等

建议逐个分类为真实缺陷、未来功能或无效注释；真实缺陷建立明确任务，避免长期 TODO 失去意义。

### 22. 示例、工具和历史子项目增加仓库噪声

仓库同时包含 website、web-ui、locale-tui、money-lab、多个 agent/claude skill、example plugin 等。它们可能有价值，但会让代码索引和全仓测试混入非 Android 主产品内容。

建议在架构文档中标明“生产必需 / 开发工具 / 示例 / 历史实验”，并为索引和 CI 提供范围标签。

## P2：安全、隐私与可靠性

### 23. 记忆、通知监听、文件、插件和 WebView 是最高隐私风险区

仓库具备长期记忆、通知读取、文件访问、插件脚本和 WebView 桥接。任何一个入口权限过宽或日志包含完整内容，都可能暴露私密对话。

建议专项检查：

- 日志是否记录完整提示词、通知正文、角色卡和记忆。
- WebView bridge 是否限制来源、方法和参数大小。
- 插件是否具备最小权限和用户可见授权。
- 导出/备份是否加密或明确提示风险。
- Android 数据提取规则是否排除敏感数据库和密钥。

### 24. `data_extraction_rules.xml` 仍有 TODO 标记

备份/设备迁移规则不能长期保持模板状态。长期记忆和 API 配置属于高敏感数据，应明确哪些可云备份、哪些只能本地。

### 25. API Provider 和 TTS 配置需要统一密钥保护

Provider、TTS、ASR 类型多，设置页体积大。应确认所有密钥均使用相同安全存储策略，不进入日志、导出和截图诊断。

### 26. 插件声明式 UI 与 WebView 桥接需要白名单审计

`PluginUIDeclarativePage.kt` 和相关 WebView 文件复杂度较高，且包含 TODO。应验证插件不能任意调用文件、通知、网络、角色记忆或系统工具。

## 文档问题

### 27. CODE_INDEX 使用说明与用户当前要求存在张力

索引文档写着“禁止无目的全仓扫描”，这是日常开发的正确规则；但本次属于明确全仓审计，应在文档中补充“全仓审计模式”的标准流程和输出格式。

### 28. README、AGENTS、重建计划和实际产品状态需要同步

当前多个文档带事故复盘、历史任务和旧基线，信息价值高，但新开发者很难区分当前规则、历史背景和已完成事项。

建议分成：

- `AGENTS.md`：只留当前强制规则。
- `docs/history/`：事故复盘与旧实施账本。
- `docs/architecture/CURRENT_STATE.md`：当前架构和真实未完成项。

## 建议修复顺序

1. 先跑当前 master 的聚焦 Kotlin 编译，确认基线。
2. 清理 Study 模块旁路实现：同名 `take`、同名 SnackbarHost、新旧页面重复。
3. 完成等级和通用碎片的真正退役策略。
4. 修复 Compact 页窄屏、角色列表滚动和收藏长列表问题。
5. 拆分 ChatService、ProactiveMessageService、MemoryBankService。
6. 建立统一数字活动事件总线，提升插件活动的共同经历感。
7. 做隐私专项审计：备份、日志、WebView、插件、密钥。
8. 归档过时计划，建立当前状态文档。
